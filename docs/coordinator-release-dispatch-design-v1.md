## 1. Binding outcome and authority

Marco has approved **one Codex Coordinator as owner of every ordinary production deployment and rollback**, not merely migrations. Individual implementation agents build, test, review, and rehearse through **demonstrated PREACTIVATION_READY**. A dormant `implementation_request` function is to become usable only after the queue/identity/capacity path is qualified; enabling it is an independent production configuration change. An approved, current implementation package can be dispatched without another redundant permission request. A prioritized queue must retain authorized implementation work when no fresh worker capacity is available; it must not use ordinary agent messages as the queue's source of truth. Coordinator can bundle compatible changes into one intentional release and alone executes the approved effect. Marco retains explicit approval for known rollback-window-closing/incompatible/destructive migrations and any other separately protected effect.

**Not granted:** approval of any specific candidate, migration, release, live flag flip, deployment, credential/permission expansion, or background scheduler. This document authorizes design-review submission only. It proposes no authorization from mail, priority, readability, a project, or model judgment.

**Ordinary-use success:** Marco approves a bounded implementation once; `implementation_request` creates one durable eligible request; the current **Codex Coordinator**, not `/root` or an arbitrary other thread, sees it, chooses the highest currently eligible work, and launches exactly one fresh authorized worker when proven capacity is available. Otherwise the request remains visible and pending. Worker returns a tested pre-activation package. Coordinator later selects an exact qualified release checkpoint, tests a ready known-stable recovery path, executes one serialized activation on separate current authority, watches real production/feedback signals, and either explicitly accepts that checkpoint or promptly restores the verified known-stable release. Migration releases follow a separately sequenced and effect-specific path.

## 3. V1 boundaries and invariants

1. **One canonical implementation request:** `task_run_requests` + exact canonical WorkId/revision/approved baseline; not messages, Asana GIDs, a new project, a new workflow engine, or a second request table.
2. **One production effect owner:** Codex Coordinator owns ordinary activation, rollback, release composition and trial disposition; existing host maintenance remains actual executor. A worker's test/landing authority never becomes production authority.
3. **Two distinct queues:** implementation backlog = authorized work awaiting worker; release backlog = exact pre-activation-ready artifacts awaiting compatibility/activation authorization. They may use views over existing WorkIds, not a duplicate authoritative store. One item reaching PREACTIVATION_READY does not make it production deployable.
4. **No unmeasured restoration claim:** 10 seconds is a **testable target** for compatible no-migration binary switchback, measured from rollback invocation to verified effective service; it is not a claim existing code meets it. Migration restoration has a separately explicit RTO and data-consequence contract.
5. **Fail closed on exact uncertainty:** stale review, changed package, unknown effect/launch, conflicting Coordinator generation, insufficient memory/capacity proof, incompatible schema, missing LKG or suspect monitoring => WAIT/UNKNOWN, not a new launch/deploy.
6. **Immutable version identities:** exact reviewed WorkId/revision; managed RunReceipt request_id/run_id; release candidate Git SHA, built runtime/image digest, configuration/migration version, prior accepted LKG; each independently read back.
7. **No background work implied by storage:** PENDING is durable state. Inactive Coordinator wake is unavailable unless a separately proven resident delivery adapter exists. No promises about offline ChatGPT/Codex execution.

## 4. Implementation queue: admission, ordering, dispatch and recovery

### 4.1 Admission

Reuse `implementation_request(api_version=1, operation_id, package_work_id, observed_revision)` unchanged for externally supplied identity. The server checks: exact CURRENT nonterminal package and unchanged revision; exact approved Human Review package or supported legacy approval; independent PRE_IMPLEMENTATION `BASELINE_PRESERVED` or supported legacy proof; current authenticated sender WorkGrant; no contradictory STOP/HOLD/dependency/authorization. The existing `ImplementationRequestState` supplies most admission checks. Add only a read-only projection of currently eligible/nonterminal requests and dependency/current priority truth; do **not** let a queue view become a second approval authority. If a current user correction supersedes approval, the existing request remains as historical evidence but is **ineligible** for launch.

For “obviously approved”, Coordinator reads typed evidence and may proceed without a *new* human permission. It must not decide approval from prose, a PR title, or messages. Missing/ambiguous current authorization ⇒ NOT_ELIGIBLE with reason.

### 4.2 Queue state / minimal interface

The source of truth is joined `task_run_requests` + `task_run_executions` + `task_run_results` + canonical WorkId/dependencies/priority. Expose one bounded, read-only **`implementation_queue_get`** projection (name provisional; prefer extension of an existing applicable read tool if identified in implementation review), returning request_id, exact package WorkId/revision, trusted approval refs, effective HUMAN HIGH/NORMAL / BEFORE / HOLD decisions, prerequisite/block reason, created_at, bound run identity or terminal outcome, and `eligibility=READY|BLOCKED|UNKNOWN|RUNNING|TERMINAL`. No payloads, secrets, raw prompts, or new project. Filter incompatible or corrupted items without dropping evidence. Allow bounded pagination and explicit count/truncation; avoid a full unbounded backlog scan.

Ordering: current human before/hold claims first; HIGH before NORMAL; stable created_at/request_id tie-break; block or skip ineligible items without starving ready ones. Agent-recommended priorities inform Coordinator judgment but cannot manufacture the human HIGH band or override a HOLD. Reprioritization changes the existing priority claim with attributable authority, not request creation time or mutable queue shadow rows. A large blocked HIGH item must not monopolize capacity needed by smaller READY work.

### 4.3 Coordinator target and wake

The target is the stable tuple `(runtime=CODEX, role=Codex Coordinator)`. Immediately before delivery, resolve a **single** current canonical mailbox record with generation, session_key, and supported runtime thread binding. Zero matches ⇒ PENDING_UNAVAILABLE; multiple/contradiction ⇒ UNKNOWN_CONFLICT. Never synthesize `/root` as a target, use name alias to authorize another thread, or send to the first Codex thread found. A successful send does **not** prove receipt or execution.

**V1 minimal credible wake path:** the already-running edge can expose a bounded pending-request observation and a noncanonical wake signal to a proven current Coordinator runtime; on service startup/connection recovery it rescans nonterminal requests. PostgreSQL NOTIFY may reduce latency but is never the durable queue. If an existing persistent delivery/outbox cannot bound lost-response and duplicate-send behavior, add exactly the smallest necessary attempt state tied to `request_id`—not an entire attention platform. Messages must not carry the scheduling state or authorize launch. The proposed Postgres attention-consumer architecture in `b047...` is **reference design only** and is optional until a supported current Codex wake adapter and need are proved. If exact native Coordinator wake is unavailable, retain request safely and fail the auto-dispatch activation test; an active Coordinator can manually inspect, but that is not completion of the requested automated journey.

### 4.4 Capacity and one-launch fence

Only the Coordinator chooses among eligible items, after reading actual native fresh-worker slots, current managed run receipts, owner obligations, and a fresh per-action `scripts/agent-resource-admission` GO/WAIT. The existing memory `max_memory_jobs` counter is **not** an idle slot. An unavailable authoritative capacity reading ⇒ WAIT; no aggressive polling or eviction of an active worker. A capacity event, worker terminal result, Coordinator reconnect, or bounded queue scan can reconsider an unchanged request.

Before host worker launch, atomically reserve `(request_id, current work revision, Coordinator mailbox generation, exact managed launch intent)` in the canonical task-run owner or a narrowly scoped reservation seam. Re-read package authorization and dependency/STOP truth at reservation. Use the existing trusted launcher `--agent-task` and server-bound `task_request_id` → `RunReceipt.run_id`; never construct a new grant in the model. The existing `bind_start` rejects a second run for one request, but because it occurs after launch preparation it **alone is insufficient** proof that two competing launchers cannot both create side effects. The implementation must either fence before spawning via one durable claim or demonstrate that the existing trusted launch is already strictly idempotent with request identity. Add **no new queue table** if this can be represented as one transition in the current request row/host reservation. Lost response ⇒ reconcile exact attempt/run on host and task-run tables; UNKNOWN blocks re-launch. Runtime STOPPED/LOST evidence is required for any successor. Result completion must be current managed-run generation and exact request; late stale results remain evidence, never terminal truth.

### 4.5 Queue lifecycle

Server-derived states for UI/Coordinator: `ADMITTED -> READY/WAITING_DEPENDENCY/WAITING_CAPACITY/COORDINATOR_UNAVAILABLE -> RESERVED -> RUNNING -> RESULT_RECORDED -> PREACTIVATION_READY | BLOCKED | FAILED | CANCELLED`. These are **projections**, not a mandate for a new state machine/table. Persist the minimum reservation/attempt fields only where crash safety cannot be derived. Cancellation/STOP prevents new launch immediately; active run requires exact supervised cessation and truthful consequences. Corrupted/missing receipts mean UNKNOWN rather than “available worker”.

Worker prepares exact code/review/CI/scripted useful E2E, host-shaped nonproduction activation/failure/rollback rehearsal, artifact and compatibility evidence, then records PREACTIVATION_READY. End-user review and protected effects remain separate. Do not silently mark a request complete at PR creation or mere CI pass.

## 5. Release orchestration: one Coordinator, selected checkpoint and known stable

**Candidate formation.** Coordinator chooses a coherent tranche after exact eligible PRs are integrated/qualified, explicitly naming included and excluded work. Freeze one immutable Git SHA and actual deployed artifact/runtime digest, relevant config hashes, migration chain, source review/CI subjects, and one exact predicted predecessor. A main-SHA checkpoint initially includes *all reachable merged content at that SHA*. Do not claim selective exclusion of already merged changes. `edge_deploy.prepare()` must stop requiring candidate == moving `origin/main` and instead verify a **specific green, immutable authorized release reference/artifact** with current composition proof. If genuine cherry-pick/selective release content is required, treat a release branch with its own qualification as a separate reviewed extension rather than smuggling it into V1.

**Release queue.** A second bounded, read-only Coordinator view over PREACTIVATION_READY packages and a local exact release manifest (prefer existing host receipt/selector ownership). It is not normal agent messages or a new generic deployment scheduler. Coordinator assembles one manifest with dependency graph and migration-order prerequisites, validates composition and current production state, serializes effect under the existing edge-maintenance host lock, and requires exact current activation authority. One release manifest covers a coherent batch, but each constituent package retains its source approval; batching does not broaden any package's authorization.

**Known-stable registry.** Product-level `ACCEPTED_LKG` is a retained immutable production release record, distinct from the **development CONTROL** selector. Proposed minimal host-owned atomic pointer/manifest (no new DB) binds runtime path/content digest, Git SHA, launcher preimage/hash, effective env/tool/schema compatibility facts, accepted_at, evidence refs, recovery command identity, and last successful rehearsal. Check source-artifact/runtime identity and host readback before adopting an initial baseline. `ACTIVE_TRIAL` points to the newly activated candidate; it MUST NOT replace `ACCEPTED_LKG` until a separate evidence-backed promotion. Retain recovery artifact and state until successor accepted. Lost/corrupt LKG ⇒ no ordinary automatic activation, explicitly UNKNOWN.

**Lifecycle.** `PREPARED` (no production effects) -> `AUTHORIZED_RELEASE` (effect-specific authority current) -> `ACTIVATING` -> `ACTIVE_TRIAL` -> `ACCEPTED_LKG` or `FAILED/RESTORED/CONTAINED/UNKNOWN`. Exact transition receipts and verified effective service/artifact identity establish actual states. A merge is not a production activation; activation is not known-good promotion; absence of errors is not success evidence. A lost Coordinator must reconcile host receipt, not initiate another attempt.

**Sole operator.** Production host executor accepts only an exact authorized Coordinator release packet, checks current effect permission and the shared lock, and leaves an emergency preapproved recovery entrypoint. Because ordinary agents may share the same Unix account on the host, **mailbox identity and procedural wording alone do not mechanically block direct shell bypass**. V1 must demonstrate a trusted server/host execution boundary that verifies Coordinator identity/authority or report that isolation is unproved and hold any claim of enforcement. Do not solve this by inventing a new privileged service without a separately scoped review. Break-glass operator recovery is separately logged and not confused with a worker-initiated deployment.

## 6. Deterministic fast rollback

**Recovery is prepared before activation.** For each compatible no-migration / demonstrably old-runtime-compatible release, the host prepares one version-pinned rollback entrypoint independent of candidate code. It knows the immutable accepted LKG, stored launcher/runtime/config, current active trial and expected state compatibility. Invocation must not require choosing a commit, rebuilding, fetching, asking an agent, or locating a backup. It owns one lock and exact receipt; reconciles interruption before another effect. It performs the minimum executable switch/restart, verifies the effective running artifact and an authenticated representative public MCP/service check, and records attempt, trigger, duration and outcome.

**10-second target:** measured from recognized rollback trigger / operator invocation until independently verified service restoration for rehearsal-qualified R0/compatible releases, including process restart and verification. Run repeated representative real-host or formally equivalent host-shaped rehearsals and record individual times/maximum and p95 (do not infer p95 from inadequate samples). No claim of success from a 0.05-second file swap. If rehearsals fail 10 seconds, report the failing bound and revise architecture/target via Human Review; never weaken silently. The existing `edge_deploy.rollback()` may stop/restart and restore DB (`dropdb`/`pg_restore`, potentially minutes and lost writes), so it is **not** the required fast standalone compatible rollback. Extend the existing host executor/receipt rather than duplicate it.

**Migration and ambiguity:** After a state-changing upgrade, old binary compatibility must be demonstrated on the *new* state, including representative reads/writes; otherwise the fast switch must be disabled. DB restore is an exceptional separately authorized recovery plan with stated possible post-backup write loss and measured RTO, not “rollback in 10 seconds”. UNKNOWN runtime/lock/upgrade effect => freeze conflicting changes, preserve gate when appropriate, report containment and reconcile. Never blindly retry a prior unresolved maintenance failure just because candidate/review changed.

## 7. Migration batching and exact human boundary

Classify each **effect boundary**, not the entire PR: (R0) no durable incompatible state mutation, fast restore proven; (compatible additive) old runtime proven on post-state and recovery rehearsed; (recoverable but slower) exact safe route and time/data impact specified; (rollback-window-closing) old version cannot return without unbounded delay, data loss, forward fix or irreversible action; (UNKNOWN) missing/conflicting proof. Current source does not contain a universally trusted final classifier or effect-specific R3 approval ingress; do not make up a new “APPROVED” field from agent prose.

Coordinator composes a **migration-aware batch plan** with explicit stop points: prepare and back up; additive expand; verify old/new binary coexistence; activate candidate; observe; later and separately authorize destructive contract/drop/cleanup. A migration with a proven compatible old runtime may share a controlled release when its authority covers the effect. Any rollback-window-closing/incompatible/destructive effect requires Marco's **specific current decision while present**, with exact consequence packet: schema/state preimage, effect, old recovery that closes, write-loss risk, feasible recovery route/time, and proof. No safe current authority -> HOLD; missing evidence -> UNKNOWN. Serialize all production DB effects with the Coordinator's one shared host execution lock. Do not batch unrelated destructive changes simply for throughput.

## 8. Monitoring, promotion and feedback

Before cutover, record baseline of authenticated public smoke, process/service health, error/failure counts, latency if available, deployed identity/schema and known open failure/feedback records. After cutover, use live production readback, WorkId-bound failure/resolution evidence (`flow_report`/`observability_get` where attributable), host receipts, error and availability signals, and triaged feedback. Absence of a signal or not-yet-accepted observability reader is UNKNOWN, not healthy. Capture correlation from exact release manifest/attempt/time to service and failure events; do not infer production attribution from branch name or an unrelated WorkId. No new dashboard or generic AI health predictor in V1.

Abort criteria established per release before go: wrong effective SHA/schema; failing public authenticated smoke; core endpoint unavailable; new severe attributable regression; loss of trusted monitor/currentness; unexpected migration effect; unreconciled failure. Deterministic compatible failures may invoke pretested rollback through the trusted Coordinator/host boundary. Ambiguous/incompatible failures stop unsafe effects, preserve containment and escalate, rather than cause automatic destructive DB restore. Coordinator accepts a trial as `ACCEPTED_LKG` only after representative real useful operations plus explicit event/failure/feedback review and final exact identity; observation duration is calibrated from evidence, not a magical fixed timer. Acceptance retains evidence and promotes atomically.

## 10. Required scripted acceptance/falsification matrix

**Queue and identity**
1. Valid reviewed package under current sender grant: one `implementation_request` creates one durable request, replay identical; no second human ask. Revoked/superseded/HOLD/changed revision blocks new pickup and existing request does not silently run.
2. Two HIGH/NORMAL eligible, one human BEFORE, one HOLD, one dependency-blocked: deterministic ordering with provenance; ready low-band request progresses when higher item blocked; no forged HIGH.
3. No fresh native slot / failed GO: PENDING with explainable reason. A verified slot+GO later launches one new Worker; no use of memory jobs as substitute for actual slot count.
4. Unique current canonical Coordinator generation: exact delivery and pickup; zero present: retained PENDING; duplicate/conflicting or stale generation: UNKNOWN and no misroute. Explicit `/root` alias cannot redirect the request.
5. Kill/restart between request commit, wake, claim, host worker start, bind, and result; reconcile exact request/receipt. No double launch, no missing request, no terminality from stale worker. STOP cancels queued work, active work recovered safely.
6. Dispatcher flag OFF -> tool absent, no worker starts; enabling on nonproduction exposes exact tool only after proof, no automatic production deploy or migration.

**Release/recovery/migration**
7. Freeze a release at a historical green SHA while origin/main advances: candidate remains exact and deploy selection is intentional; if main-only contract remains, fail qualification rather than deploy unrelated changes.
8. Two compatible preactivation-ready changes compose one exact authorized batch with dependency graph; unrelated/excluded changes explicitly visible. Concurrent deployment requests serialize through existing lock and exact effect receipt.
9. Prepare accepted LKG and fully rehearse rollback before go. Deliberately broken compatible trial -> one command restores actual public authenticated MCP and old SHA <=10 seconds measured end to end, with failures/variance recorded. Test lost response after switch and recovery receipt reconciliation.
10. TRIAL cannot overwrite LKG; sufficient representative live operations plus error/failure/feedback readback permits explicit ACCEPTED, not elapsed quiet alone. Monitoring outage => UNKNOWN, not automatic promotion.
11. Additive migration: old runtime and new schema compatibility proved by read/write/semantic E2E; switchback does not restore DB. Destructive/incompatible migration/unknown schema/previous unresolved effect => effect HOLD/UNKNOWN and exact human consequence packet; no destructive automatic fallback.
12. Simulated supervisor loss, missing backup, invalid LKG manifest, corrupted receipt, mismatched current public identity or live health failure: preserve effective state/containment and report UNKNOWN; never produce false restored/PASS evidence.
13. Shared-host bypass check: a normal implementation worker attempts direct deploy; if same-UID host control permits it, record **mechanical Coordinator-only enforcement NOT_PROVEN** and block its acceptance until an authorized trusted boundary exists.
14. Review the full activation path, not microbenchmarks: preactivation setup, authority, host operation, restart, public verification, rollback and rescue all use actual elapsed receipt-based timing. Repeat in safe disposable environment and then on approved production-like host boundary.

## 11. Risks, assumptions, alternatives and human-owned remainder

**Material risks:** (a) shared Linux user can bypass procedural Coordinator-only routing; (b) no existing authoritative native free-agent count exposed to this ChatGPT service; (c) current `bind_start` alone is not a proven pre-spawn fence; (d) no current main attention consumer guarantees asynchronous wake; (e) current deployment main-only check and database restoration defeat curated checkpoint and fast rollback; (f) schema/data compatibility limits LKG; (g) absent failure records cannot establish health; (h) candidate/source advancement invalidates evidence if not checked; (i) adding privilege/service/schema state may inflate operational burden. Each must be falsified in its owning slice; do not claim a ready-to-activate platform today.

**Options:** use ordinary messages as backlog — rejected (poor priority, authoritativeness and replay); add a project/second queue table — rejected for V1 (duplicates canonical request state); enable existing `implementation_request` alone — rejected as **insufficient** (creates inert task request); build an entirely new dispatcher daemon + deployment engine — rejected for size/duplicate truth; preferred: derived queue over existing task-run, minimal current-gen wake/claim seam, existing managed launch, existing host maintenance, atomic host release/LKG marker and real E2E proof.

**Human choice already resolved:** all production deployments/rollbacks belong to Coordinator, worker preactivation only, migration rollback-closing effects require Marco. **Open consequential choice to surface after independent review if needed:** whether mechanical Coordinator-only enforcement requires a new privileged host boundary because same-UID scripts remain bypassable; and whether a non-main cherry-picked release branch is essential rather than an immutable selected-green-main SHA. Neither choice is silently authorized by this design review.

**Post-review action:** owner receives independent DESIGN verdict on exact WorkId/revision and Git commit, challenges/disposes findings, and returns any surviving material human-owned choice to Marco. On PASS, prepare a compact Human Review proposal for the independently scoped V1 first slice and implementation authorization; **do not auto-submit Human Review, code dispatch, feature flag enablement, deployment, migration or activation**. Reviewer evaluates this candidate against current exact code and ownership, challenges needless machinery, verifies all 14 tests and the smallest true vertical path, and is not coached toward PASS.
