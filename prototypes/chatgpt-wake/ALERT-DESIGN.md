## Incident policy and trust boundary

Armed bindings continue normal mailbox-ID polling even when closed. Pending nonempty plus `bound-tab-missing` starts an immediate incident. Pending nonempty plus continuously observed `draft-present` starts after60 seconds; no draft text, attachments or formatting are read or copied. Persist incident UUID, exact endpoint/generation, pending-ID evidence, first/last observation time, and send/recovery operation IDs in existing binding storage. A restart or observation gap exceeding two normal polling intervals resets an unqualified draft timer; it cannot manufacture60 seconds of continuous observation. New IDs during the same blocked episode do not create more alerts. Busy, STOP/disarm, source unavailable and ambiguous original UI sends never masquerade as these two causes. UNKNOWN remains UNKNOWN; no original UI send retry.

Extend the existing authenticated loopback JSON report with typed incident/recovery state and endpoint/generation, not arbitrary text. Host checks exact current binding and advisory pending IDs with existing generation-fenced observer. Require actual matching pending IDs before an incident alert; never trust reported counts alone. The browser is the observer of tab/draft condition, not a source of mailbox authority. The host generates a fixed bounded payload containing name, reason, metadata/IDs and this Work reference. No drafts or message bodies. Keep existing Host/loopback, no-CORS, report capability, JSON and size guards.

Reserve deterministic alert/recovery MessageIds in persisted incident state before request. Shared durable mail replay by sender/message identity and unchanged arguments is the authoritative dedupe. Retain exact normalized report/send arguments, including the evidence used for first creation; a repeated operation with changed arguments is conflict, never a second message. ORDERING: under CURRENT host grant and reporter-binding admission, FIRST look for the committed exact sender/MessageId and compare its frozen arguments. If it matches, return the authoritative original receipt before checking current pending evidence or re-resolving the observed target binding. Cleared pending IDs or a changed observed mailbox generation cannot turn a committed send into a new incident or hide its receipt. Only a first creation checks live pending evidence/current observed binding and resolves the current fixed recipient. Retain the committed envelope for replay; do not rebuild it from current pending IDs or a new recipient generation. A reporter's own revoked/stale admission still fails closed. Test commit followed by lost response, pending cleared/observed binding changed, then exact retry returns the same receipt with no second send; changed arguments conflict. On ambiguous response reconcile only that identity; no new incident ID as retry. Confirmed submitted mail is `queued`, not delivered/read/processed; expose returned MessageId/DeliveryId. If an incident is active, one recovery message follows an observed clear cause (empty pending or positively observed former blocker cleared), not an observation failure, STOP or disarm. Recoveries reference the original incident without assuming its delivery. Revoked/expired sender means visible reporting unavailable and retained incident, not fake success.
